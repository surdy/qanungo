# instructions-editor

The write-posture half of qanungo's instructions doctor (qanungo#11). `qanungo doctor` computes the *finding* — near-duplicate instructions clustered across sessions of one repository, each quoted once (scrubbed) and cited by transcript `source_hash`; this skill reads those clusters with the user and, where they agree one belongs in an instruction file, proposes the edit as a diff. qanungo stays read-only and never opens a checkout; the edit happens here, in the harness, in the repo, under the user's own permission prompts.

## Steps

1. **Run the command.** `qanungo doctor` — no positional argument, and **no default window**: absent `--last`, it reads all of the archive's history, which is what "have I been repeating myself" means. Add `--last 4w` only when the user deliberately narrows (`h`/`d`/`w` units — no `m` by design). It folds *transcripts*, not summaries, so a cold run downloads the archive; say so before starting one, and let the footer report what it cost.
2. **Read the document as repetition, not as diagnosis.** Output: a scope line (sessions read, user messages, how many the harness wrote rather than the user, how many were comparable), the preamble stating what the tool cannot see, the thresholds that produced everything below, then **Repeated instructions** grouped by repository — each cluster `**N occurrences across M sessions**`, one scrubbed blockquote of the fullest wording, and a citation per occurrence (`archived <date> · event <n> · <source_hash>`). Then **Friction**, **Not examined for repetition**, **Gaps**, and the instrumentation footer.
3. **Triage the clusters before proposing anything.** Not every cluster is an instruction. The document says out loud that its harness-noise list is a floor rather than a proof, and real runs leave residue: injected skill bodies, prompts pasted from elsewhere, a question the user simply likes asking. Read each blockquote and sort it with the user into *an instruction I keep having to give*, *a workflow I keep having to describe* (that is a skill or a command, not a CLAUDE.md line), and *noise*. Say which bucket each one is in and why; never carry a cluster forward the user has not agreed is real.
4. **Then, and only then, open the repository.** `qanungo` never looked at it. Read the actual `CLAUDE.md` / `AGENTS.md` — and any nested or imported instruction file the repo uses — in the working tree, under the harness's normal permission prompts. Three outcomes, and they are different answers: the file already says it, so the finding is that the instruction is being ignored or is badly placed rather than missing; the file says something weaker or contradictory, so the edit is a sharpening; there is no such line, or no such file at all, so the edit is an addition — and creating a file is a bigger ask than adding a line, so ask.
5. **Propose the smallest edit, as a diff, and never silently.** One cluster, one focused edit; show the diff and wait for approval before writing. Word it from the user's own repeated wording rather than from your paraphrase of it, and put it where the file's existing structure says it belongs. Never bundle unrelated instruction changes into one edit, and never rewrite the file's voice while you are in there.
6. **Say what each edit traces to.** Every proposed line names the cluster behind it: the occurrence count, the session count, and at least one `source_hash`. A line you cannot trace to a cluster is your idea rather than a finding — you may still suggest it, but say so in those words and keep it out of the traced set.
7. **Use Friction as corroboration only.** The per-repository counts of messages that arrived after a failing tool are a coarse proxy the document itself hedges; a repository with more friction is a place to *look*, never evidence for a particular line. Never present a friction number as the reason for an edit.
8. **Carry the coverage.** Repositories under "Not examined for repetition" were read and not compared — one with a single session in the reach cannot produce a cluster however much re-explanation happened in it, and a session the archive attributes to no repository has no instruction file to belong to. A non-empty Gaps section is sessions that contributed nothing at all. Say these out loud rather than letting the answer imply the archive had nothing to show.

## What this skill must not claim

- **No causality.** The doctor reports repetition. It cannot see whether an instruction file exists, what it says, or whether anything would have gone differently — and the document says exactly that in its own preamble. "You had to repeat this because your `CLAUDE.md` is missing it" is a sentence no reading of a transcript supports. The honest form is "you gave this instruction in four sessions; the file does not mention it; would a line about it help?"
- **No before/after claim.** Measuring whether an edit actually reduced repetition is **V2** (qanungo#11's differentiator) and does not exist yet: nothing in the archive marks when an instruction file changed, so no run can currently split a window on that event. Do not tell the user the doctor will show them the improvement, and do not manufacture a comparison by re-running over a shorter window — changing the reach changes what is counted, not what improved. Re-running in a few weeks shows a *later* window, which is worth doing and is not a measurement.
- **No reconstruction behind a marker.** See below.

## Redaction boundary (qanungo#8)

The doctor's excerpts are **already redacted, default ON** — `[REDACTED:<pattern>]` markers are load-bearing, and the footer names the pattern revision and counts what fired. This skill writes *files*, so the rule is stricter here than anywhere else in `contrib/`: **never reconstruct what a marker hides into an instruction file.** If the repeated instruction was "always use the token `[REDACTED:github-token]` for the staging deploy", the edit names *which* credential and *where it lives*, never the credential itself — and if the line cannot be written without the hidden value, that is a sign it does not belong in a committed file at all. Never ask the archive, the transcript, or the user to un-redact one so it can be pasted. Never pass `--no-redact` on your own initiative; if the user asks for it, note that off is a deliberate choice for their own local reading, that the footer confesses it in bold by design, and that its output must not be copied into a file either.

## Boundaries

- **Read-only to the archive; write-only to the user's own instruction files.** Nothing here writes to munshi, to Patwari, or to qanungo's cache, and nothing here edits source code — an instruction file is the whole of this skill's write surface.
- **Clusters never cross repositories, by construction**, so a finding is always about one repository's files. The same instruction repeated in two repositories is two findings and, if it belongs anywhere shared, a user-level `~/.claude/CLAUDE.md` question the user has to decide — say that rather than editing two repositories on your own initiative.
- **A cluster spans conversations, not session ids.** A resumed session replays what came before it, and the doctor merges those into one conversation before counting, so "across 2 sessions" already means two separate sittings.
- **The thresholds are arbitrary-until-measured constants**, stated in the document itself: phrase length, the overlap two messages need, the minimum length of a comparable message, and the sessions a cluster must span. A cluster is what those settings found; the absence of one is not proof that nothing was repeated, and the empty result is phrased in exactly those terms.
- The instrumentation footer is for coverage and cost questions; drop it from a polished answer, and keep the citations.
- Related lanes: `/coach` reads the practice scores, `/ask` searches history, and `session-recall` opens a transcript once a session identity is in hand. This is the only skill in the set that proposes a write.
